# 03 — UI (`ui`)

**Archivos:** `app/components/**`, `app/lib/{site,motion,cluster-topology}.ts`

## Estructura

| Carpeta | Componentes |
|---------|-------------|
| `ui/` | `Window` (ventana de terminal/editor: barra con path + `aside` opcional), `Section` (comando decorativo + h2 mono + intro), `ButtonLink` (primary ámbar / secondary con borde), `ExternalLink` (mono, cian), `icons.tsx` |
| `layout/` | `ScrollChoreography` (client: GSAP + ScrollTrigger + Lenis), `IntroScreen` (boot screen), `SiteHeader` (prompt `matias@speroni:~$` como link a `#top`, nav como `./Projects`…), `SiteFooter` (status line con el build) |
| `scene/` | `HeroScene` (client: monta el 3D), `ClusterScene` (Three.js / R3F, chunk aparte), `ClusterSvg` (versión SVG para celulares, server) |
| `sections/` | `Hero`, `Projects` + `ProjectCard`, `Experience`, `Stack`, `About`, `Contact` + `ContactForm` (client) |

## Metáfora por sección ("Ops console", ver capa 02)

| Sección | Comando (`SECTION_COMMANDS`) | Forma |
|---------|------------------------------|-------|
| Hero | `whoami` | nombre + rol a la izquierda; a la derecha una terminal que corre `git push` y las **etapas reales del CI** (`PIPELINE`), luego `cat profile.yml` |
| Projects | `ls ~/projects` | cada proyecto es una `Window` con `~/projects/<slug>`; el primero (y un último impar) ocupa todo el ancho |
| Experience | `git log --graph --career` | línea de rama con un nodo por empresa; roles con fechas; highlights como líneas `+` |
| Stack | `cat stack.yml` | una `Window` con YAML: grupo = clave (h3), ítems = lista con logo, `detail` como comentario `#`; números de línea por CSS; 2 columnas en desktop |
| About | `cat README.md` | foto, bio, facts como `clave: valor`, educación y certificaciones |
| Contact | `./contact.sh` | canales directos + formulario en una `Window` |

Todo el copy de la metáfora (líneas de boot, pipeline, comandos) vive en `app/data/console.ts`.

## Terminal del hero

Server component, **sin JavaScript**: los tiempos se pasan como variables CSS (`--at`, `--done`,
`--chars`) y la animación vive en `globals.css` (capa 02). Constantes `START`, `STAGE_GAP`, `STAGE_RUN`
en `Hero.tsx`. La terminal es `aria-hidden` (`data-testid="hero-terminal"`): repite datos que ya están
en el texto del hero.

## Clúster 3D del hero (Three.js / React Three Fiber)

- Red de servidores: `buildClusterTopology` (`lib/cluster-topology.ts`, determinista con semilla, testeada)
  da nodos sobre un elipsoide y aristas a los 3 vecinos más cercanos. La misma red se dibuja en WebGL y en SVG.
- `ClusterScene`: nodos `instancedMesh` + contorno wireframe fusionado en una sola geometría + cables
  (`lineSegments`) + ~70 paquetes (`points` con blending aditivo) que hacen un random walk por el grafo;
  cada nodo se ilumina cuando le llega un paquete. Gira lento, se inclina con el puntero y con el scroll la
  cámara se aleja (lee `heroScroll.progress`, un objeto mutable, no estado React).
- Estado por frame en `useRef` (el React Compiler prohíbe mutar valores de `useMemo`).
- `HeroScene`: solo con `(min-width: 768px)` y WebGL; se monta en `requestIdleCallback` con `next/dynamic`
  (`ssr: false`, three.js nunca está en la carga inicial); `frameloop="never"` fuera de pantalla y
  `"demand"` (un cuadro quieto) con reduced motion.
- Celulares: `ClusterSvg` (server, sin JS), paquetes por CSS `offset-path`.

## Coreografía de scroll (`ScrollChoreography`, GSAP + ScrollTrigger)

Un solo client component en el layout; las secciones siguen siendo server y marcan qué se mueve:

| Atributo | Efecto |
|----------|--------|
| `#top` + `[data-hero-copy]` / `[data-hero-term]` | parallax a distinta velocidad; escribe `heroScroll.progress` |
| `[data-command]` | el comando se tipea (`clip-path` con `steps(n)`) |
| `[data-section-title]` | el h2 sube después del comando |
| `[data-reveal]` | ventanas/cards entran con leve inclinación 3D, escalonadas (`ScrollTrigger.batch`, una vez) |
| `[data-branch]` / `[data-node]` | la rama del git log se dibuja con el scroll; los nodos aparecen con rebote |
| `#stack .code-line` | stack.yml se imprime línea por línea |

GSAP y Lenis se importan dinámicamente y **solo con movimiento permitido**; Lenis solo en desktop con
puntero fino (`lib/motion.ts`). Nada está oculto en el HTML: si el JS no corre, todo se ve.

## Contratos

- ids de sección = `NAV_ITEMS` (`SectionId`); Hero es `#top`, main `#main`. `SECTION_COMMANDS` es un
  `Record<SectionId, string>`: una sección nueva no compila sin su comando.
- Imágenes: `next/image`. Logos del stack sin optimizar (SVG chicos) sobre un cuadradito claro (hay logos negros).
- Links externos: `ExternalLink`, `ButtonLink external` o `target="_blank" rel="noopener noreferrer"`.

## Accesibilidad (axe en CI, con y sin reduced motion)

- Un solo h1 (`Matias Speroni`).
- Prompt del header: texto visual + nombre `sr-only` ("Matias Speroni, back to top").
- Decorativo y `aria-hidden`: comandos sobre cada título, paths de las ventanas, terminal del hero,
  `./` de la nav, `+`/`-`/`:`/`#` de la sintaxis, puntos de las ventanas.
- Axe revisa contraste también del texto `aria-hidden`: por eso `fg-subtle` es `#7d8fa9`.
- Formularios con `label htmlFor`, `aria-invalid`, `aria-describedby`, `role="alert"`/`"status"`.

## Rendimiento

Carga inicial: Next + `ContactForm` + componentes livianos. GSAP/Lenis y three.js son chunks dinámicos
(three solo en ≥768px, en idle). Lighthouse CI mide en cada push (job "Lighthouse budgets"; performance solo avisa).
